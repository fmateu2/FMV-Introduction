01 / The system

Separate execution.
Shared agreements.

Each realm runs its own Maester process, with a terminal, inventory, route configuration and alliance state. Realms exchange sigils, establish alliances, request goods and send orders through a custom TCP protocol.

I co-developed the project around a practical systems question: how do independent execution flows coordinate without blocking the interactive command loop?

01

Delegate work to processes.

Persistent envoys are created with fork(). Two pipes per worker carry missions and results between parent and child.

02

Handle incoming connections.

A listener thread accepts TCP sockets. Detached connection threads interpret frames while the main command loop stays available.

03

Coordinate state and transfers.

Mutexes protect shared updates. Fixed frames carry messages; larger files use chunked transfers, acknowledgments and MD5 integrity checks.

Project context. The trading workflow is part of a fictional realm simulation. The engineering focus is process coordination, communication and persistence.

A JavaScript illustration of serialization, not a running C process or TCP connection. Origin is fixed at 127.0.0.1:18890. The six field cards are not drawn to scale. A matching checksum establishes format integrity, not sender authentication.


The engineering focus
The project brings together several kinds of concurrency: child processes for outgoing missions, threads for incoming connections, and an event loop monitoring terminal input and worker pipes. Making the boundaries explicit is what keeps the design understandable.
The protocol is equally explicit: fields are serialized individually, partial reads are accumulated, and the receiver validates the completed frame before dispatching it.
03 / Inside the C code
Where coordination becomes code.
Three excerpts from the system I co-developed, with the data flow and design decisions made explicit.
01
Define the wire format field by field.
The serializer writes a byte buffer explicitly. It does not send the in-memory Frame struct, which could contain compiler padding.
src/network/protocol2.c · serialize_frameC ↓
ORIGINAL SOURCE EXCERPT
void serialize_frame(const Frame *frame, unsigned char buffer[FRAME_SIZE]) {
    uint16_t net_len;
    uint16_t checksum;
    int offset = 0;

    memset(buffer, 0, FRAME_SIZE);

    if (frame == NULL) {
        return;
    }

    buffer[offset++] = frame->type;

    memcpy(buffer + offset, frame->origin, ORIGIN_SIZE);
    offset += ORIGIN_SIZE;

    memcpy(buffer + offset, frame->destination, DESTINATION_SIZE);
    offset += DESTINATION_SIZE;

    net_len = htons(frame->data_length);
    memcpy(buffer + offset, &net_len, sizeof(uint16_t));
    offset += sizeof(uint16_t);

    memcpy(buffer + offset, frame->data, DATA_SIZE);
    offset += DATA_SIZE;

    checksum = compute_frame_checksum(buffer);
    checksum = htons(checksum);
    memcpy(buffer + offset, &checksum, sizeof(uint16_t));
}
  1. Zero the complete 320-byte buffer so unused payload bytes have a defined value.
  2. Copy each fixed-size field and write the length using htons for network byte order.
  3. Sum the first 318 bytes, then store the checksum in the final two bytes.
ILLUSTRATIVE WALKTHROUGH
1 type + 20 origin + 20 destination + 2 length
+ 275 data/padding + 2 checksum = 320 bytes
A five-byte payload still occupies a 320-byte frame.
02
Reassemble a full frame from partial reads.
TCP is a byte stream. One read call may return fewer bytes than the application requested, so the receiver accumulates progress.
src/network/net_frame.c · read_fullC ↓
ORIGINAL SOURCE EXCERPT
int read_full(int fd, unsigned char *buf, size_t size) {
    size_t total = 0;

    while (total < size) {
        ssize_t n = read(fd, buf + total, size - total);
        if (n <= 0) {
            return -1;
        }
        total += (size_t)n;
    }

    return 0;
}
  1. Track how many bytes have already been received.
  2. Read into the remaining buffer space and advance the offset by the actual byte count.
  3. Return success only after the full frame arrives. An error or closed connection returns failure.

Accumulated bytes:         80 → 200 → 320

03
Give each envoy its own execution flow.
Two pipes create separate task and result channels. fork() creates the child; each side closes the pipe ends it does not use.
src/state/envoy2.c · envoy creationC ↓
ORIGINAL SOURCE EXCERPT
if (pipe(to_envoy) < 0 || pipe(from_envoy) < 0) {
    free(envoys);
    return NULL;
}

pid = fork();
if (pid < 0) {
    close(to_envoy[0]);
    close(to_envoy[1]);
    close(from_envoy[0]);
    close(from_envoy[1]);
    free(envoys);
    return NULL;
}

if (pid == 0) {
    /* Child: close parent-side ends of this envoy's pipes */
    close(to_envoy[1]);
    close(from_envoy[0]);

    /* Close parent-side ends of all previously created envoys */
    for (j = 0; j < i; j++) {
        close(envoys[j].fd_write);
        close(envoys[j].fd_read);
    }

    envoy_worker_loop(to_envoy[0], from_envoy[1]);
    close(to_envoy[0]);
    close(from_envoy[1]);
    _exit(0);
}
  1. Create one pipe for tasks and another for results before forking.
  2. In the child, close the parent-side ends and previously inherited worker descriptors.
  3. Run the persistent worker loop; the parent later uses its remaining descriptors to dispatch missions and collect results.
ILLUSTRATIVE WALKTHROUGH
Parent writes a mission → child reads its task pipe
Child sends TCP frames  → remote realm handles the request
Child writes a result   → parent observes its result pipe
