01 / The problem

Separate files. Connected questions.

The project starts with CSV datasets covering environmental observations, country-level energy records, sector emissions, power plants, living costs and government policies. The task is to turn those sources into a coherent relational database that can support analytical questions.

It spans conceptual modeling, table design, keys and relationships, data import, analytical SQL and database-side logic.

02 / My contribution

From the model to the queries.

My work covered part of the conceptual model and support for the relational design, schema execution and imports for assigned entities in Oracle, a share of the advanced queries and validation statements, trigger implementation and the report.

Contribution scope documented in the original team report. The project was developed collaboratively.

    01

    Give each record a precise identity.

    An energy record is identified by country, year and energy type. Foreign keys connect it to the three corresponding parent tables.

    sql/schema.sql · Yearly_Energy_RecordsORACLE SQL
    ORIGINAL SOURCE EXCERPT
    CREATE TABLE Yearly_Energy_Records (
    country_name VARCHAR(255),
    year_number INT,
    type_name VARCHAR(255),
    energy_consumption FLOAT,
    energy_production FLOAT,
    co2_emission FLOAT,
    PRIMARY KEY (country_name, year_number, type_name),
    FOREIGN KEY (country_name) REFERENCES Country(country_name),
    FOREIGN KEY (year_number) REFERENCES Year_(year_number),
    FOREIGN KEY (type_name) REFERENCES Energy_Type(type_name)
);
    1. The composite primary key makes the combination unique, rather than requiring the country alone to be unique.
    2. Records can share a country and year when their energy types differ.
    3. Foreign keys require matching country, year and type rows in the parent tables.
    ILLUSTRATIVE WALKTHROUGH
    (Arbor, 2015, solar) + (Arbor, 2015, wind): two distinct records
A second (Arbor, 2015, solar): duplicate primary key
Arbor is fictional; referenced parent rows must exist.
    02

    Trace Query 03 from rows to a result.

    A small fictional dataset makes the energy-balance query easier to follow. These are teaching values, not results from the project’s original dataset.

    Example input · year 2015 for every row
    CountryTypeProductionConsumption
    Arborsolar4025
    Arborwind6045
    Baysolar3050
    Baywind2030
    1. JOIN links each energy record to its country. WHERE keeps only 2015.
    2. GROUP BY collects each country’s rows. SUM calculates its production and consumption totals.
    3. HAVING keeps groups whose production exceeds consumption. SELECT returns their country names.
    ILLUSTRATIVE WALKTHROUGH
    Arbor: production 100 > consumption 70 → included
Bay:   production  50 < consumption 80 → excluded
Query result: Arbor
The example uses distinct energy types without aggregate-total rows.
    05 / Database-side logic

    Record changes where the data lives.

    The source includes trigger definitions for power-plant status auditing, policy-budget alerts and environmental-observation classification, with three auxiliary tables.

    The report records the team’s original implementation and validation work. Reproducing the complete pipeline requires the original CSVs and an Oracle environment; those were not part of this portfolio verification.

    06 / What I would improve next

    Make the data pipeline reproducible.

    The next step is to script the staging setup, document dataset provenance, validate date and key consistency, and add repeatable query and trigger tests. Historical comparisons also need explicit treatment of aggregate rows and policy time periods.
