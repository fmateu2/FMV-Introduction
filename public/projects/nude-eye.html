01 / The application

My work on Nude Eye.

I co-developed Nude Eye with Jan Francesc Porcar Guillen for our Object-Oriented Design and Programming course. Our application lets users select or register a client, browse products and provider offers, build a shopping cart, complete a simulated purchase and review purchase history.

The later project phases introduce specialized customer and product behavior while preserving the existing flow. That makes the project a practical exercise in extending a working system through clear contracts.

03 / PERSISTENCE

Contracts & adapters

Four DAO interfaces separate managers from their API and file-backed implementations.

Constructor-based dependency injection allows managers to receive persistence implementations. At startup, the original controller checks the course API and attempts local files if API access or initialization fails.

A precise boundary: the application selects its persistence mode at startup. The two stores are not replicated or automatically synchronized.

05 / Inside the code

Design decisions you can read.

Three excerpts from the Java project I co-developed, connecting the UML diagram to concrete behavior.

01

Let each product define its own price.

ContactLens overrides the shared calculatePrice method. The caller uses a common product contract while the subtype supplies the calculation.

src/business/ContactLens.java · calculatePriceJAVA ↓
ORIGINAL SOURCE EXCERPT
public float calculatePrice(float sellingPrice, boolean applyVAT) {
    if (applyVAT) {
        return sellingPrice * PricingConstants.CONTACT_LENS_VAT_MULTIPLIER;
    }
    return sellingPrice;
}
  1. Receive the selling price and whether the assignment’s VAT multiplier applies.
  2. Use the contact-lens multiplier when requested; otherwise return the original price.
  3. Keep the variation in the subtype, so callers do not need a separate pricing branch for every product.
ILLUSTRATIVE WALKTHROUGH
Base price: €40.00
applyVAT = true  → 40 × 1.10 = €44.00
applyVAT = false → €40.00
The multiplier is an assignment constant.
02

Pass in a storage implementation.

The manager depends on ProductDAO. This constructor accepts an implementation, keeping the business-layer entry point consistent across storage adapters.

src/business/ProductManager.java · injected constructorJAVA ↓
ORIGINAL SOURCE EXCERPT
public ProductManager(ProductDAO productDAO) {
    this.productDAO = productDAO;
}
  1. The constructor receives the DAO rather than creating one itself.
  2. ProductJSONDAO and ProductAPIDAO implement the same persistence contract.
  3. A test double could implement that contract too, allowing manager behavior to be tested without the course service.
ILLUSTRATIVE WALKTHROUGH
Local setup: ProductJSONDAO → ProductManager
API setup:   ProductAPIDAO  → ProductManager
Caller:      getAllProducts()
The manager delegates the read to the selected DAO.
03

Translate storage failures into domain errors.

findById keeps the caller focused on catalogue behavior while preserving an underlying persistence exception as its cause.

src/business/ProductManager.java · findByIdJAVA ↓
ORIGINAL SOURCE EXCERPT
public Product findById(String productId) throws BusinessException {
    try {
        Product product = productDAO.findById(productId);
        if (product == null) {
            throw new ProductNotFoundException("Product not found.");
        }
        return product;
    } catch (PersistenceException e) {
        throw new BusinessException("Error accessing product data.", e);
    }
}
  1. Ask the selected DAO to find the requested product ID.
  2. A missing product produces ProductNotFoundException; a found product is returned.
  3. A storage failure becomes BusinessException with its original cause, keeping persistence concerns behind the business interface.
ILLUSTRATIVE WALKTHROUGH
Existing ID     → return Product
Missing ID      → ProductNotFoundException
Storage failure → BusinessException, preserving its cause
This explains the source; it is not a Java execution log.
06 / Engineering perspective

Designing for the next change.

The project connects inheritance, polymorphism, exception handling and persistence contracts in one application. The report also explains how those choices evolved through successive assignment phases.

A next iteration would add focused tests around pricing and persistence, use decimal money values, make expiry calculations independent of the system clock and strengthen authentication before any real deployment.
